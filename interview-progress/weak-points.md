### 0. 编译 vs 解释 vs JIT（Q54 / Q78 复考 → 二刷 38/40 已掌握 ✅）
- **问题**：把 JIT 理解成「保存到本地后改解释」；与 Git 混淆（语音转写）
- **要记住**：
  - **编译（javac）**：`.java` → **字节码** `.class`，编译期完成，与平台无关
  - **解释（Interpreter）**：JVM **启动时**逐条解释执行字节码，启动快、无需等编译
  - **JIT（Just-In-Time）**：某段代码被**频繁调用**（方法调用计数器达阈值）→ JIT 把字节码**编译成本地机器码**并缓存 → 后续**直接执行机器码**，更快
  - **方向**：解释 →（热点）→ JIT 编译，**不是**编译后变解释
  - **口诀**：先解释保启动，热点 JIT 换性能
- **Q78 复考表现（16/40 仍较差）**：用户主动答，仍混淆——① 把 javac 说成「字节码转机器码」（实为 JIT 职能，搞反）；② 解释器答对（逐行）✅；③ JIT 只说出「计数器/阈值+保存复用」，漏「**编译成机器码**」这关键一步，最后说「这其实就是编译」但主语不明。**结论：主干仍未真正掌握，需二次复考**。已现场画图 + 给标准三句话话术，要求背熟。
- **Q78 二刷表现（38/40 通过）**：用户主动复述，三个角色**全部正确**——① javac 把 Java 编译成**字节码**文件；② 解释器启动后**逐行解释字节码**并运行；③ JIT 计数器达**阈值**时把这部分字节码**转成机器码并缓存**。对比首刷 16 分是质的飞跃，不再混淆 javac 与 JIT 职能。**结论：已真正掌握，#0 从 🔴 高优先级复考池移除**。

### 1. 泛型与泛型擦除（Q9 11/40 → Q42 33 → Q43 32 → **Q79 复考 34/40 已掌握 ✅**）
- **Q79 复考表现（34/40 通过）**：用户主动作答，主干全部正确——① 泛型=类型参数化、T 是占位符、出现在类/方法/接口 ✅；② 擦除=编译后去掉类型信息、取值/传参处插强转 ✅；③ **为什么擦除=兼容 Java 1.4、避免大改** ✅（亮点，往年没答出）；④ 不能 new T()（擦除后运行时不知具体类）、不能泛型数组（数组要运行时类型信息）✅。
- **残留 gap（不影响掌握）**：① 因果表述小瑕——"类型安全是因为擦除"应为"泛型先在编译期做类型检查保证安全，然后才擦除以兼容"；② 漏答「重载冲突」（`f(List<String>)` 与 `f(List<Integer>)` 擦除后签名相同，不能同时存在）；③ `instanceof List<String>` 不行的原因（运行时无泛型信息）辅导时已讲清。
- **结论**：已真正掌握，#1 从 🔴 高优先级复考池移除。

### 2. final 与不可变类（Q2/Q37/Q38 → Q80 15 → **二刷 34/40 已掌握 ✅**）
- **问题**：曾混淆 final 类 = 对象不可变；把「不可变类」理解成「用 final 修饰」
- **Q80 二刷表现（34/40 通过）**：① final 类/字段/方法三层含义全对 ✅；② 不可变类说出 final + private final + 无 setter + 防御性拷贝 ✅。残留：可再强调「final **类**」与陷阱 `final StringBuilder` 仍可变。
- **要记住**：
  - `final` **类** = **不能被继承**（如 `String`、`Integer`），≠ 对象不可变
  - `final` **字段** = **引用不能改**，引用指向的对象内容仍可能变
  - 不可变类四件套：`final` 类 + `private final` 字段 + 无 setter + 可变字段防御性拷贝
  - **关键陷阱**：`final StringBuilder name` 仍可变，因为 StringBuilder 内容可 append
- **结论**：已真正掌握，#2 从 🔴 高优先级复考池移除。

### 9. Stream API
- **问题**：不知道中间操作 vs 终端操作；stream 理解成「单线程」
- **要记住**：
  - 懒执行原因：**等终端操作触发才真正执行**，便于优化（短路、合并操作），不是因为「能链式调用」
  - 终端操作（collect/count/forEach）触发真正计算，返回结果
  - `stream()` = 顺序流；`parallelStream()` = 并行流，适合 CPU 密集 + 大数据量
- **易错**：I/O 密集不适合 parallelStream；没有终端操作中间操作不执行

### 10. 内部类
- **问题**：混淆创建方式；「静态内部类无法被实例对象修改」表述不清
- **要记住**：
  - 非静态内部类 **依赖外部类实例**，隐式持有外部类 `this` 引用
  - 静态内部类 **不依赖**外部类实例，类似静态成员
  - 创建：`outer.new Inner()` vs `new Outer.StaticInner()`
  - 访问：非静态可访问外部实例成员；静态只能访问外部 static 成员

### 11. JVM 内存区域（静态 vs 实例变量）
- **问题**：知道共享/独享区别，不知道存哪
- **要记住**：
  - 静态变量 → **方法区**（JDK 8+ 叫 **元空间 Metaspace**）
  - 实例变量 → **堆 Heap**（随对象一起分配）
  - 静态变量类加载时初始化，只有一份

### 12. BigDecimal（Q21/Q22 → **Q81 复考 28/40 基本过关**）
- **问题**：曾用 `new BigDecimal(0.1)` — 面试第一陷阱
- **Q81 表现**：知道要用**字符串**构造 ✅；知道直接传数字有问题 ✅；缺「为什么」（double 无法精确表示 0.1）
- **要记住**：
  - `0.1 + 0.2` = `0.30000000000000004`（背完整）
  - ✅ `new BigDecimal("0.1")` 或 `BigDecimal.valueOf(0.1)`
  - ❌ `new BigDecimal(0.1)` — 0.1 先变成不精确的 double 再传入
  - 运算：`bd1.add(bd2)` 返回新对象，不能写 `bd1 + bd2`
- **结论**：构造选型已掌握，降为低优先级；面试时记得补一句「double 精度」原因

### 14. 字符串常量池
- **问题**：以为 `new String("abc")` 只创建 1 个对象
- **要记住**：
  - `new String("abc")` 通常 **2 个对象**（池中 "abc" + 堆上新 String）
  - `"abc"` 字面量先进**字符串常量池**（JDK7+ 在堆中）
  - `String s = "abc"` 直接复用池中引用，不 new
  - `==` 比较地址，字面量相同则 `true`

### 15. 抽象工厂扩展性（OCP 陷阱）
- **问题**：以为给产品族加新产品「直接新增创建方法就行」；没意识到抽象工厂接口要改
- **要记住**：
  - 抽象工厂 = 一个接口里**每种产品类型对应一个创建方法**；加**新产品类型**（新轴，如加耳机）必须**改接口**加方法 → 所有具体工厂都要实现 → 违反开闭原则
  - 抽象工厂擅长的是加**新产品变体**（同轴另一种实现，如小米家族代替华为家族）：只加一个具体工厂子类，不动接口
  - 对比工厂方法：加产品 = 加一个具体 Creator 子类实现 factoryMethod，**不改动已有代码**，OCP 更友好
  - **口诀**：抽象工厂「横向加家族易、纵向加新品难」；工厂方法「加产品易、加家族要加一堆类」

### 16. 策略模式（重要考点，已辅导 + Q76 复考 + 已基本掌握）
- **来源**：Q76 前辅导（用户要求记为重要考点）；Q76 实答 27/40；Q76 复考 32/40
- **要记住**：
  - 定义：行为型设计模式；把一族**可互换算法/行为**封装成独立类，定义统一接口，让它们**运行时互相替换**，客户端面向接口、不关心具体是哪个
  - 三角色：Strategy 接口（定义算法方法）/ ConcreteStrategy 具体策略（各自实现）/ Context 上下文（**持有** Strategy 引用，业务里只管调它）
  - 本质 vs if-else：if-else 把算法写在调用方内部、加算法改旧方法（违反 OCP）、难测试；策略模式把算法独立成类、加算法只加新类不动旧代码、可**运行时切换**、每个算法可单测
  - 代价：类数量变多；客户端需了解有哪些策略（常配工厂/枚举解决）
  - ⚠️ **何时不用**：只有「一族会频繁增减的算法/行为」才值得；偶尔两三个固定分支 if-else 更简单
  - **工厂 vs 策略（Q76 答错，重点联动）**：工厂模式 = 负责「**创建哪个对象**」（生产）；策略模式 = 负责「**用哪个算法/行为**」（使用/选择）。两者常搭档：工厂来**生产**策略对象，策略来**使用**算法。口诀：工厂管生，策略管用
- **Q76 表现**：行为型 ✅、OCP ✅、何时不用 ✅；但定义不完整（漏运行时替换）、三角色没说全、工厂/策略分工说反 ❌

- **复考后动作**：设计模式复考名单里策略模式移除 / 降优先级；后续若再抽可只考「现场写三行代码」
- **要记住**：
  - 定义：**行为型**设计模式；把一族**可互换算法**封装成独立类，定义统一接口，运行时互相替换

### 17. JNI 代价与好处细节（Q77 30/40，主干已掌握，细节待补）
- **来源**：Q77 native/JNI；用户答 30/40（良好），主干全对但有细节缺口
- **要记住**：
  - 完整调用流程不能漏 **System.loadLibrary("xxx")**：JVM 把 .so/.dll 加载进进程，并把 native 方法绑定到 C 函数地址；之前还需把 .c 编译成平台动态库（Linux .so / Windows .dll / macOS .dylib）
  - 代价补全：① 跨 JNI 边界有**类型转换/marshalling 开销**，且 **JIT 无法跨越边界做内联优化**（别用它包超小热路径）；② **native 内存手动管理**——jstring/jobject 用完要 ReleaseStringUTFChars/DeleteLocalRef，引用分 Local/Global，否则泄漏甚至 OOM；③ native 代码崩了 = 整个 JVM 崩（无异常保护）
  - 好处补全：复用已有 C/C++ 库（OpenCV、加密、音视频编解码）、性能极致敏感底层、访问 Java 标准库没暴露的系统/硬件能力
  - JNIEnv*：C 函数里 JVM 传入的指针，用来操作 Java 对象/字段/方法、做类型转换
- **复考聚焦**：只考「loadLibrary 这一步 + 代价/好处完整清单」，不必重考主干
- **Q77 表现**：native 无方法体 ✅、生成 .h ✅、写 .c ✅、JNI 双向桥（含回调 JVM）✅、拖垮 JVM + 底层用 C ✅；缺口如上 3 点
