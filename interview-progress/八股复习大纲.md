## 二、复习笔记（按模块）

### [PRJ] 项目经历问答 · P0

#### [PRJ-01] 业务背景怎么讲

- **是什么**：用 30～60 秒说清「给谁用、解决什么问题、核心链路」。
- **为什么/原理**：面试官先听业务，再听技术；业务不清，后续难点无锚点。
- **面试怎么答**：
  1. 这是一个面向 ___（用户）的 ___（系统），核心流程是 ___ → ___ → ___。
  2. 我负责 ___ 模块，日均量级约 ___（QPS/订单/消息，没有就说峰值或表规模）。
  3. 该模块直接影响 ___（体验/资金/履约），所以对正确性/性能有要求。
- **易错点 / 追问**：只堆技术栈不讲业务；量级全靠猜；讲不清上下游。

#### [PRJ-02] 职责与模块边界

- **是什么**：明确「我做了什么 / 没做什么 / 和谁协作」。
- **为什么/原理**：边界清晰才显得真实，避免「全栈包办」被拆穿。
- **面试怎么答**：
  1. 我负责：需求落地、接口设计、核心表/缓存、联调与线上问题。
  2. 不负责：___（如基础设施、前端、别的域）。
  3. 协作：和 ___ 通过接口/MQ/文档约定。
- **易错点 / 追问**：把团队成果全归自己；说不清表结构与接口字段。

#### [PRJ-03] 难点-方案-结果模板

- **是什么**：每个难点固定「现象 → 原因 → 方案 → 取舍 → 结果」。
- **为什么/原理**：面试官听的是问题解决闭环，不是名词堆砌。
- **面试怎么答**（填空模板）：
  1. **现象**：出现了 ___（慢/超卖/不一致/超时）。
  2. **定位**：通过 ___（日志/慢 SQL/监控）发现 ___。
  3. **方案**：采用 ___（索引/缓存/锁/异步），备选是 ___，放弃是因为 ___。
  4. **结果**：___ 指标从 ___ 到 ___；若无数据，说「稳定性改善 / 故障次数下降」并诚实说明。
- **易错点 / 追问**：只有方案没有结果；方案与业务目标无关；无法画时序图。

#### [PRJ-04] 八股挂接点清单

- **是什么**：把项目难点映射到 MySQL/Redis/并发/MQ 等考点。
- **为什么/原理**：一面常「项目 → 追问八股」；提前挂接可控节奏。
- **面试怎么答**：见本文「四、项目面试提纲」表格。
- **易错点 / 追问**：挂接点说不出原理；项目没用过却硬吹。

### [JB] Java 基础 · P0

> 主材料：`Java-Basic.md`；薄弱点见 `weak-points.md`

#### [JB-01] 跨平台 / JDK-JRE-JVM

- **是什么**：源码 → 字节码；不同平台装不同 JVM；一次编译到处运行的是程序不是 JVM。
- **为什么/原理**：字节码统一，平台差异由各平台 JVM 消化。
- **面试怎么答**：
  1. `javac` 生成 `.class` 字节码，不直接生成机器码。
  2. JVM 负责加载、解释/JIT、内存与 GC。
  3. JRE = JVM + 核心库；JDK = JRE + 编译调试工具。
- **易错点 / 追问**：说「JVM 跨平台」；把 JVM 说成纯解释器（见 JB-02）。

#### [JB-02] 编译 vs 解释 vs JIT 🔴

- **是什么**：javac 编译期出字节码；运行期先解释；热点由 JIT 编成本地机器码缓存。
- **为什么/原理**：解释保启动；热点 JIT 换吞吐。方向是「解释 → JIT」，不是「编译后再变解释」。
- **面试怎么答**：
  1. 编译（javac）：`.java` → 平台无关字节码。
  2. 解释：JVM 启动后逐条解释执行，启动快。
  3. JIT：方法调用计数达阈值 → 字节码编译为本地机器码并缓存 → 后续直接跑机器码。
  4. 口诀：先解释保启动，热点 JIT 换性能。
- **易错点 / 追问**：🔴 Q54 方向反了；JIT ≠ Git；Java = 半编译半解释。

#### [JB-03] 泛型擦除 🔴

- **是什么**：泛型提供编译期类型检查；擦除后运行时几乎看不到 `<T>` 参数信息。
- **为什么/原理**：兼容旧 JVM；`T` 是占位符，具体类型如 `String` 不会被「擦没对象」。
- **面试怎么答**：
  1. 作用：编译期类型安全、少强转、提高复用。
  2. 擦除：编译后去掉泛型参数信息，约等于按上限（常为 Object）处理。
  3. 不能 `new T()` / `new T[]`：运行时无足够类型信息创建。
  4. 替代：`Class<T>` + 反射，或用 `List<T>` 代替数组。
- **易错点 / 追问**：🔴 与多态混淆；以为擦除发生在运行时才发现；JVM 仍知对象真实类。

#### [JB-04] final 与不可变类 🔴

- **是什么**：`final` 类 = 不能继承；不可变类 = 对象状态创建后不可改。
- **为什么/原理**：final 字段只锁引用，不锁对象内部可变状态。
- **面试怎么答**：
  1. final 类 ≠ 对象不可变（如 `final StringBuilder` 仍可 append）。
  2. 不可变四件套：final 类 + private final 字段 + 无 setter + 可变成员防御性拷贝。
  3. String 不可变：内部状态不可改 + 修改返回新对象 + 常量池/hash/安全等收益。
- **易错点 / 追问**：🔴 Q2/Q61 把 final 类当不可变；Q38 忽略 StringBuilder 可变。

#### [JB-05] BigDecimal 🔴

- **是什么**：十进制精确运算类型，金额场景首选。
- **为什么/原理**：`double` 二进制无法精确表示 0.1；`0.1+0.2=0.30000000000000004`。
- **面试怎么答**：
  1. 金额用 BigDecimal，不用 double 直接算。
  2. ✅ `new BigDecimal("0.1")` 或 `BigDecimal.valueOf(0.1)`。
  3. ❌ `new BigDecimal(0.1)`（先变成不精确 double）。
  4. 运算用 `add/subtract/...`，返回新对象，不能 `+`。
- **易错点 / 追问**：🔴 Q22 仍用 double 构造；比较用 `compareTo` 不用 `equals`（尺度不同）。

#### [JB-06] String 不可变 / 常量池

- **是什么**：String 内容不可改；字面量进常量池（JDK7+ 在堆）可复用。
- **为什么/原理**：安全、缓存 hash、常量池共享；修改生成新对象。
- **面试怎么答**：
  1. 不可变 ≠ 仅靠 final 类，要看内部 char/byte[] 不可被外部改。
  2. `"abc"` 复用池；`new String("abc")` 通常池中字面量 + 堆上新对象（常说 2 个）。
  3. `intern()`：池中有则返回池引用，无则放入。
- **易错点 / 追问**：🔴 Q35 以为 new 只 1 个对象；final≠不可变。

#### [JB-07] == equals hashCode

- **是什么**：`==` 比引用（基本类型比值）；`equals` 默认同 `==`，可重写比内容。
- **为什么/原理**：HashMap 先 hash 定位桶，再 equals 判等；二者必须契约一致。
- **面试怎么答**：
  1. 重写 equals 必须重写 hashCode。
  2. hashCode 返回 int，不是 boolean。
  3. Integer 缓存 -128～127，`==` 可能 true；超出则 false。
- **易错点 / 追问**：说 hashCode「返回 true」；只改 equals 不改 hashCode。

#### [JB-08] 面向对象三特性 / 重载重写

- **是什么**：封装隐藏细节；继承复用扩展；多态同一消息不同响应。
- **为什么/原理**：重载编译期按参数定；重写运行时按实际类型定（动态绑定）。
- **面试怎么答**：
  1. `Animal a = new Dog()`：编译看左（能调什么），运行看右（调谁的实现）。
  2. 字段不参与多态。
  3. 多态价值：解耦、开闭、面向接口扩展。
- **易错点 / 追问**：只会背定义无代码例子；多态作用只说「有层次」。

#### [JB-09] 抽象类 vs 接口

- **是什么**：抽象类抽共性可含状态；接口定能力契约，可多实现。
- **为什么/原理**：单继承限制 → 接口补多行为；Java8+ default/static 支持平滑扩展。
- **面试怎么答**：
  1. 抽象类不能 `new`（匿名内部类除外）；可有普通方法与字段。
  2. 接口无构造函数；方法含抽象/default/static（Java9+ private）。
  3. `final` 抽象类不合法：final 禁继承，抽象需被继承。
- **易错点 / 追问**：🔴 default 不熟；「接口方法必须重写」不严谨。

#### [JB-10] 异常体系 🔴

- **是什么**：Throwable → Error / Exception；Exception 分受检与非受检。
- **为什么/原理**：受检强制编译期声明/处理；划分看是否 `RuntimeException` 子类。
- **面试怎么答**：
  1. Error 严重通常不捕获；Exception 可处理。
  2. 受检也是**运行时抛出**，只是编译期强制处理。
  3. finally 几乎总执行；finally 里 return 会覆盖 try 的返回值（慎用）。
- **易错点 / 追问**：🔴 把受检叫「编译时异常」；throws（声明）vs throw（抛出）。

#### [JB-11] 反射 🔴

- **是什么**：运行时获取类信息并动态创建/调用。
- **为什么/原理**：靠 Class/Method/Field/Constructor；Spring IoC、注解、框架大量使用。
- **面试怎么答**：
  1. 场景：框架注入、注解处理、通用工具、动态代理。
  2. 缺点：性能差、破坏封装、安全风险。
  3. 注意：是 IoC 不是「iop」。
- **易错点 / 追问**：🔴 Q46 说不出常用类与性能缺点。

#### [JB-12] 装箱拆箱 / Integer 缓存

- **是什么**：基本类型 ↔ 包装类；`valueOf` 对小整数有缓存。
- **为什么/原理**：集合/泛型只能存对象；缓存减少小对象创建。
- **面试怎么答**：
  1. 自动装箱拆箱由编译器插入 `valueOf`/`xxxValue`。
  2. 循环里 `Integer sum += i` 会产生大量临时对象，注意性能。
  3. `-128～127` 的 `==` 可能相等。
- **易错点 / 追问**：比较包装类用 `==`；NPE 拆箱空对象。

#### [JB-13] 类加载初始化顺序

- **是什么**：`new Son()` 时父静态 → 子静态 → 父实例块+构造 → 子实例块+构造。
- **为什么/原理**：类先初始化再实例化；父先于子。
- **面试怎么答**（6 步）：
  1. 父类 static（变量+静态块，按出现顺序）
  2. 子类 static
  3. 父类实例变量 + 实例代码块
  4. 父类构造
  5. 子类实例变量 + 实例代码块
  6. 子类构造
- **易错点 / 追问**：漏实例代码块；把父构造插到子 static 前。

#### [JB-14] Stream 懒执行 🔴

- **是什么**：中间操作返回 Stream 且延迟；终端操作才真正计算。
- **为什么/原理**：便于短路与融合优化，不是「因为能链式所以懒」。
- **面试怎么答**：
  1. 中间：filter/map；终端：collect/forEach/count。
  2. 无终端操作，中间操作不执行。
  3. `parallelStream` 适合 CPU 密集 + 大数据；I/O 密集慎用。
- **易错点 / 追问**：🔴 因果说反；以为 stream 只能单线程。

#### [JB-15] 内部类 / 静态变量内存位置

- **是什么**：非静态内部类持有外部类 this；静态内部类不依赖外部实例。
- **为什么/原理**：静态成员类加载初始化；实例随对象进堆。
- **面试怎么答**：
  1. 创建：`outer.new Inner()` vs `new Outer.StaticInner()`。
  2. 静态变量 → 方法区/元空间（JDK8+）；实例变量 → 堆。
- **易错点 / 追问**：🔴 不知道静态变量存哪；创建语法混淆。

#### [JB-16] BIO / NIO / AIO

- **是什么**：BIO 同步阻塞；NIO 同步非阻塞+多路复用；AIO 异步回调。
- **为什么/原理**：连接数上来后一线程一连接扛不住 → Selector。
- **面试怎么答**：
  1. BIO：一连接一线程，简单但扩展差。
  2. NIO：线程自己处理就绪事件；Netty 基于 NIO/Reactor。
  3. AIO：系统完成后回调，Java 落地相对少。
- **易错点 / 追问**：把 NIO 说成异步；说不清 Netty 选型一句。

### [COL] 集合框架 · P0

> 主材料：`Java-Collection.md`

#### [COL-01] 集合总览 List/Set/Map

- **是什么**：List 有序可重复；Set 唯一；Map 键值映射（Key 唯一）。
- **为什么/原理**：场景不同选不同结构，避免「只会 ArrayList/HashMap」。
- **面试怎么答**：
  1. List：ArrayList / LinkedList。
  2. Set：HashSet（HashMap）、LinkedHashSet、TreeSet（红黑树）。
  3. Map：HashMap、LinkedHashMap、TreeMap、ConcurrentHashMap。
  4. Collection 是接口；Collections 是工具类。
- **易错点 / 追问**：说 Set「绝对无序」（实现类不同）；Map 继承 Collection（否）。

#### [COL-02] ArrayList vs LinkedList

- **是什么**：动态数组 vs 双向链表。
- **为什么/原理**：数组随机访问 O(1)；链表插入删除改指针，但定位仍可能 O(n)。
- **面试怎么答**：
  1. 读多写少、随机访问 → ArrayList。
  2. 频繁头尾插删可考虑 LinkedList，实际业务仍常 ArrayList。
  3. ArrayList 扩容约 1.5 倍；非线程安全。
- **易错点 / 追问**：认为链表任意位置插都是 O(1)（忽略遍历成本）。

#### [COL-03] HashMap 结构与 put

- **是什么**：JDK8 = 数组 + 链表 + 红黑树；拉链法解决冲突。
- **为什么/原理**：链表过长查询退化；树化把最坏降到 O(log n)。
- **面试怎么答**：
  1. hash → 算桶下标；空桶直接放；冲突则链表/树查找 equals。
  2. 链表长 ≥8 且容量 ≥64 树化；≤6 退回链表。
  3. 允许一个 null key；非线程安全。
- **易错点 / 追问**：树化阈值只说 8 不提容量 64；多线程只说死循环（1.8 更常见覆盖丢失）。

#### [COL-04] HashMap 扩容与 2^n

- **是什么**：负载因子默认 0.75；容量为 2 的幂，扩容翻倍。
- **为什么/原理**：`hash & (n-1)` 代替取模；2^n 保证位运算均匀高效。
- **面试怎么答**：
  1. size > capacity * loadFactor 触发 resize。
  2. 新容量 2 倍，重新分布（高低位）。
  3. Key 宜不可变（如 String），避免 hash 变化丢数据。
- **易错点 / 追问**：说不清为何必须 2^n；自定义 Key 不重写 equals/hashCode。

#### [COL-05] ConcurrentHashMap

- **是什么**：并发 Map；1.7 分段锁，1.8 CAS + synchronized 锁桶头 + 红黑树。
- **为什么/原理**：粒度比 Hashtable 整表锁更细，吞吐更高。
- **面试怎么答**：
  1. 空桶 CAS 插入；有冲突 synchronized 锁链表/树头。
  2. 读多靠 volatile，不阻塞读（语义上注意弱一致性迭代）。
  3. 不允许 null key/value（与 HashMap 不同）。
- **易错点 / 追问**：还在只背 Segment；以为完全强一致快照。

#### [COL-06] HashSet / TreeSet

- **是什么**：HashSet 基于 HashMap；TreeSet 基于 TreeMap 有序。
- **为什么/原理**：Set 的 add 本质是 Map 的 put(key, PRESENT)。
- **面试怎么答**：
  1. 去重靠 hashCode + equals（Hash）或 compareTo（Tree）。
  2. 要插入顺序用 LinkedHashSet；要排序用 TreeSet。
- **易错点 / 追问**：TreeSet 元素不可比较会报错；只重写 equals 不重写 hashCode 导致「去重失败」。

#### [COL-07] 并发集合选型

- **是什么**：CopyOnWrite、BlockingQueue、ConcurrentLinkedQueue 等场景不同。
- **为什么/原理**：写少读多可 COW；生产消费阻塞用 BlockingQueue。
- **面试怎么答**：
  1. CopyOnWriteArrayList：写时复制，适合读多写少。
  2. BlockingQueue：线程间传递任务/削峰。
  3. 不要用 Vector/Hashtable 当现代方案，优先 JUC。
- **易错点 / 追问**：COW 写放大；队列选错导致 OOM（无界）。

### [CON] 并发基础 · P0

> 主材料：`xmind-md/3. Java并发篇.md`

#### [CON-01] 进程线程 / 三大特性

- **是什么**：进程是资源单位；线程是调度单位；并发要原子性/可见性/有序性。
- **为什么/原理**：共享堆导致竞态；指令重排与缓存导致可见性问题。
- **面试怎么答**：
  1. Java 线程与 OS 线程 1:1（HotSpot 常见模型）。
  2. synchronized 可保三者；volatile 保可见与有序，不保原子。
  3. 工具：锁、CAS、并发集合、线程池。
- **易错点 / 追问**：线程安全只提加锁；说不清有序性。

#### [CON-02] synchronized

- **是什么**：互斥锁，锁对象 monitor；可修饰方法/代码块。
- **为什么/原理**：同一时刻一线程进临界区；退出释放，保证可见。
- **面试怎么答**：
  1. 实例方法锁 this；静态方法锁 Class。
  2. 可重入；异常会释放锁。
  3. 与 wait/notify 配合在同一把锁上。
- **易错点 / 追问**：锁字符串常量池导致意外全局锁；锁粒度过大。

#### [CON-03] volatile

- **是什么**：保证可见性、禁止特定重排；不保证复合操作原子性。
- **为什么/原理**：写穿到主存；读绕开陈旧缓存；内存屏障。
- **面试怎么答**：
  1. 适合「一写多读状态标志」。
  2. `i++` 仍要原子类或锁。
  3. 单例双重检查需要 volatile 防指令重排。
- **易错点 / 追问**：以为 volatile 等于线程安全万能药。

#### [CON-04] CAS / 原子类

- **是什么**：Compare-And-Swap 乐观更新；AtomicInteger 等封装 CAS。
- **为什么/原理**：无锁自旋减少线程切换；失败重试。
- **面试怎么答**：
  1. 期望值匹配才更新，否则自旋。
  2. ABA 问题可用版本号/AtomicStampedReference。
  3. 高竞争下自旋消耗 CPU，需权衡。
- **易错点 / 追问**：只说无锁不说 ABA；与 synchronized 适用场景不分。

#### [CON-05] 线程池参数与拒绝策略

- **是什么**：核心线程、最大线程、队列、存活时间、工厂、拒绝策略。
- **为什么/原理**：复用线程控资源；队列满再扩到 max，再拒绝。
- **面试怎么答**：
  1. 流程：核心满 → 入队 → 队列满建到 max → 拒绝。
  2. CPU 密集 ≈ 核数+1；IO 密集可更大。
  3. 禁止 Executors 无界队列快捷方法；手动 ThreadPoolExecutor 并命名线程。
  4. 拒绝：Abort / CallerRuns / Discard / DiscardOldest。
- **易错点 / 追问**：Cached 无线程上限导致 OOM；说不清队列与 max 关系。

#### [CON-06] ReentrantLock / 死锁

- **是什么**：显式锁，可公平、可中断、可 tryLock；死锁是循环等待。
- **为什么/原理**：比 synchronized 更灵活；死锁四条件：互斥、占有等待、不可抢占、循环等待。
- **面试怎么答**：
  1. 必须 finally unlock。
  2. 防死锁：固定加锁顺序、超时、减少锁范围。
- **易错点 / 追问**：忘记 unlock；公平锁当默认必选项。

#### [CON-07] ThreadLocal

- **是什么**：线程本地变量副本，避免共享。
- **为什么/原理**：每个线程 ThreadLocalMap；弱引用 key 防泄漏需 remove。
- **面试怎么答**：
  1. 场景：用户上下文、SimpleDateFormat 隔离（现代多用 DateTimeFormatter）。
  2. 线程池场景必须 `remove`，否则串数据/泄漏。
- **易错点 / 追问**：当「线程安全容器」乱用；线程池忘清理。

### [SQL] MySQL · P0

> 材料：`xmind-md/6. MySQL篇.md`；项目细节待补充

#### [SQL-01] 索引与 B+ 树

- **是什么**：InnoDB 用 B+ 树索引；叶子存数据（聚簇）或主键（二级索引）。
- **为什么/原理**：矮胖树少磁盘 IO；叶子链表利范围扫。
- **面试怎么答**：
  1. 适合：高区分度、常作 WHERE/JOIN/ORDER BY。
  2. 不适合：低区分度（性别）、小表、频繁更新字段。
  3. 联合索引最左前缀；区分度高的放前面。
- **易错点 / 追问**：索引越多越好；说不清回表与覆盖索引。

#### [SQL-02] 事务隔离级别

- **是什么**：RU / RC / RR / Serializable；InnoDB 默认 RR。
- **为什么/原理**：隔离越高异常越少，并发越差。
- **面试怎么答**：
  1. 脏读、不可重复读、幻读对应关系要能背。
  2. RC：每次读最新提交；RR：快照 + 间隙锁防幻（了解级说清）。
  3. 提交：结合项目说用的级别与原因（待补充）。
- **易错点 / 追问**：默认级别说错；幻读与不可重复读分不清。

#### [SQL-03] MVCC / 锁

- **是什么**：多版本读；行锁/间隙锁/临键锁；undo/redo。
- **为什么/原理**：读写少阻塞；写写靠锁；崩溃恢复靠 redo。
- **面试怎么答**：
  1. 读用 ReadView + undo 版本链。
  2. 更新加行锁；范围更新可能间隙锁。
  3. 长事务易锁等待/死锁，应短事务。
- **易错点 / 追问**：以为 MVCC 解决一切写冲突；死锁只重启不分析。

#### [SQL-04] SQL 优化与慢查询

- **是什么**：慢日志定位 + EXPLAIN 看执行计划 + 改写/加索引。
- **为什么/原理**：全表扫、回表多、索引失效是常见根因。
- **面试怎么答**：
  1. 先 EXPLAIN：type、key、rows、Extra。
  2. 失效：对索引列函数/隐式转换、前导模糊 `%xx`、违反最左前缀。
  3. 优化：覆盖索引、减少 select *、分页优化、拆 SQL。
- **易错点 / 追问**：无慢 SQL 案例（待补充项目）；只会加索引不加分析。

#### [SQL-05] 聚簇索引与主键选型

- **是什么**：InnoDB 数据按聚簇索引组织；优先自增主键。
- **为什么/原理**：自增顺序插减少页分裂；UUID 乱序写放大。
- **面试怎么答**：
  1. 有主键用主键聚簇；否则唯一非空列；再否则隐式 row_id。
  2. 业务主键慎作聚簇；二级索引叶子存主键故主键宜短。
- **易错点 / 追问**：盲目 UUID 主键；联合主键过长。

### [HC] 高并发场景题 · P1

> 无真实高并发项目时：讲清「保护谁、算法差异、挂哪一层、拒绝后怎么办」即可；勿编造 QPS。  
> ★ 当前优先：`[HC-01]` 限流（流控）

#### [HC-01] 限流（总述）

- **是什么**：在单位时间内限制通过的请求数/速率，让系统在过载时仍可控。
- **为什么/原理**：资源有上限（线程池、DB 连接、CPU）；不加流控会雪崩；限流是「主动丢/延迟一部分」，换整体可用。
- **面试怎么答**：
  1. 目标：保护下游（DB/第三方/本机线程池），不是提高峰值吞吐。
  2. 常见算法：固定窗口、滑动窗口、漏桶、令牌桶（见子条）。
  3. 落地分层：网关/Nginx → 应用（Sentinel/自研）→ 方法级；分布式用 Redis + Lua。
  4. 超限策略：直接拒绝（429）、排队、降级兜底；配合熔断，不只限流。
  5. 维度：全局限流 / 按 IP / 按用户 / 按接口。
- **易错点 / 追问**：只背算法名说不清差异；单机限流在多实例下失效（要集群限流）；限流后无用户提示/监控。

#### [HC-01a] 固定窗口计数器

- **是什么**：把时间切成固定窗口（如 1 秒），窗口内计数，超阈值拒绝。
- **为什么/原理**：实现最简单（计数器 + 过期重置）。
- **面试怎么答**：
  1. Redis：`INCR key` + 首次 `EXPIRE`；或 Guava/`AtomicLong` 单机版。
  2. 缺点：**临界突刺**——前一秒末 + 后一秒初各打满，瞬时可接近 2 倍阈值。
- **易错点 / 追问**：以为固定窗口「绝对平滑」；忘记 key 过期导致永久限死。

#### [HC-01b] 滑动窗口

- **是什么**：统计「最近 T 时间内」的请求数，窗口随时间滑动。
- **为什么/原理**：缓解固定窗口边界突刺，更贴近真实速率。
- **面试怎么答**：
  1. 实现：时间戳队列 / 多小格加权（如 10 个 100ms 格子）。
  2. 比固定窗口准，比令牌桶实现略重。
  3. Redis 可用 ZSET：member=请求唯一 id，score=时间戳，清窗外再 `ZCARD`。
- **易错点 / 追问**：与固定窗口说不清区别；ZSET 方案内存与清理成本。

#### [HC-01c] 漏桶（Leaky Bucket）

- **是什么**：请求进桶，以**恒定速率**流出；桶满则拒绝（或阻塞）。
- **为什么/原理**：强制输出平滑，保护下游「匀速消化」。
- **面试怎么答**：
  1. 适合：下游处理能力恒定、要削尖峰。
  2. 缺点：无法应对短时突发（桶满直接拒），即使系统瞬时有余力也不放行。
- **易错点 / 追问**：和「削峰 MQ」混淆——漏桶是同步路径限速；MQ 是异步缓冲。

#### [HC-01d] 令牌桶（Token Bucket）★ 最高频

- **是什么**：以固定速率往桶里放令牌；请求要拿到令牌才通过；桶有容量上限。
- **为什么/原理**：平均速率受放令牌速度约束，同时允许**短时突发**（桶里积攒的令牌）。
- **面试怎么答**：
  1. 参数：放令牌速率 r、桶容量 b → 平均 ≤ r，突发最多 b。
  2. 对比漏桶：令牌桶更常用于 API 限流（兼顾平滑与突发）；漏桶更「死板匀速」。
  3. 落地：Guava `RateLimiter`（单机近似）；分布式 Redis Lua 扣令牌；Sentinel 也有类似思想。
- **易错点 / 追问**：说不清「突发」从哪来；和漏桶对调了优缺点。

#### [HC-01e] 落地位置与拒绝

- **是什么**：限流挂在哪一层、超限怎么回。
- **为什么/原理**：越靠前拦截，越省后端资源；越靠后越精细（按业务规则）。
- **面试怎么答**：
  1. **网关/Nginx**：第一道，防刷、全局限流。
  2. **应用内（Sentinel 等）**：按资源/接口/用户；可配排队、降级。
  3. **Redis + Lua**：多实例共享配额，原子扣减防超卖式超限。
  4. 拒绝：HTTP 429 / 业务码；重要读可降级缓存；写可提示重试。
  5. 挂项目（诚实）：`leetcode-tracker` 未做；若扩展「Excel 大文件导入」，可对 `/api/import` 做单机令牌桶，防打满 Tomcat 线程。
- **易错点 / 追问**：只限应用、网关被打穿；多实例各限各的导致总流量翻倍。

#### [HC-01f] 限流 vs 熔断 vs 降级

- **是什么**：三者都是稳定性手段，触发条件与动作不同。
- **为什么/原理**：限流防过载；熔断防雪崩（下游已病）；降级保核心体验。
- **面试怎么答**：
  1. **限流**：我还健康，但请求太多 → 丢掉/延迟多余请求。
  2. **熔断**：下游错误率/超时过高 → 短时间快速失败，避免拖死自己。
  3. **降级**：资源紧张 → 关非核心功能（推荐、验证码加强、只读缓存）。
  4. 一套组合拳：网关限流 + 接口限流 + 依赖熔断 + 非核心降级。
- **易错点 / 追问**：三个词混用；熔断后不会半开恢复（了解 Sentinel/Hystrix 即可）。

#### [HC-02] 削峰填谷

- **是什么**：峰值流量用队列缓冲，后端平稳消费。
- **为什么/原理**：瞬时尖峰打垮 DB；异步化拉长处理时间窗口。
- **面试怎么答**：
  1. 入口快速应答 + MQ 异步。
  2. 消费者限速、扩容、失败重试进死信。
  3. 结合库存/下单链路讲（待补充）。
- **易错点 / 追问**：队列无限堆积无告警；同步链路假装削峰。

#### [HC-03] 库存 / 秒杀思路

- **是什么**：高并发减库存防超卖，兼顾体验。
- **为什么/原理**：热点行锁/库存字段是瓶颈，需前置过滤与分层。
- **面试怎么答**：
  1. 前端/网关限流 → 缓存预减 → DB 条件更新（version/库存>0）。
  2. 下单异步化；防刷与幂等。
  3. 诚实说项目是否真做过秒杀；没有则讲「库存扣减」一般方案。
- **易错点 / 追问**：只 Redis 减不管落库；无幂等导致重复单。

### [JVM] JVM · P1

> 材料：`xmind-md/4. Java虚拟机篇.md`；基础会话已覆盖部分 GC

#### [JVM-01] 运行时数据区

- **是什么**：堆、虚拟机栈、本地方法栈、程序计数器、元空间；直接内存另计。
- **为什么/原理**：线程私有 vs 共享；GC 主要管堆。
- **面试怎么答**：
  1. 堆：对象实例，分新生代/老年代。
  2. 栈：栈帧=局部变量表+操作数栈等。
  3. 元空间：类元数据，本地内存，替代永久代。
  4. 🔴 静态变量在元空间侧；实例在堆。
- **易错点 / 追问**：常量池位置（JDK7+ 堆）；直接内存泄漏。

#### [JVM-02] GC 算法与分代

- **是什么**：判断存活用可达性分析；年轻代复制，老年代标记整理等。
- **为什么/原理**：朝生夕死用复制便宜；老对象多用整理减碎片。
- **面试怎么答**：
  1. GC Roots：栈引用、静态、常量、JNI 等。
  2. Minor GC：Eden 满；Full GC：老年代/元空间压力等。
  3. 收集器了解 CMS/G1 即可（低停顿、Region）。
- **易错点 / 追问**：年轻代说成标记清除；`System.gc()` 当必回收。

#### [JVM-03] 类加载双亲委派

- **是什么**：加载→验证→准备→解析→初始化；双亲委派先交给父加载器。
- **为什么/原理**：保证核心类唯一；防止核心 API 被篡改。
- **面试怎么答**：
  1. 启动类/扩展/应用加载器层次。
  2. 父能加载则不让子加载。
  3. 打破场景：SPI、热部署、Tomcat（了解）。
- **易错点 / 追问**：说不清「为什么要双亲」；与初始化顺序混淆。

### [MQ] 消息队列 · P2

#### [MQ-01] 异步解耦削峰

- **是什么**：生产者发消息，消费者异步处理；服务间松耦合。
- **为什么/原理**：同步链路变短；流量尖峰进队列。
- **面试怎么答**：
  1. 适用：通知、下游非核心、流量波动大。
  2. 不适用：强一致同步结果必须马上返回（或需回调/查询）。
  3. 项目挂接（待补充）。
- **易错点 / 追问**：所有调用都改 MQ；无超时与监控。

#### [MQ-02] 可靠性与幂等

- **是什么**：不丢、不重（或可接受重复）、有序（按需）。
- **为什么/原理**：网络失败导致至少一次投递常见，消费端必须幂等。
- **面试怎么答**：
  1. 生产：确认机制 / 事务消息（按中间件）。
  2. 消费：手动 ack；失败重试；死信队列。
  3. 幂等：唯一键、状态机、去重表。
- **易错点 / 追问**：只保证生产不保证消费；无幂等却「正好一次」。

#### [MQ-03] Kafka vs RabbitMQ 选型（待补充）

- **是什么**：Kafka 高吞吐日志流；RabbitMQ 灵活路由传统业务消息。
- **为什么/原理**：模型不同（分区日志 vs 交换器队列）。
- **面试怎么答**：按项目实际用的讲，不会的不硬吹。
- **易错点 / 追问**：背对比表却没用过。

### [MS] 微服务基础 · P2

#### [MS-01] 单体 vs 微服务

- **是什么**：单体一进程部署；微服务按业务拆多服务独立部署。
- **为什么/原理**：拆分换独立扩展与组织边界，代价是分布式复杂度。
- **面试怎么答**：
  1. 单体：简单、事务容易；到一定规模部署与协作变难。
  2. 微服务：独立扩缩、技术异构；引入网络、一致性、可观测性成本。
  3. 按团队规模与域边界选型，不是越大越好。
- **易错点 / 追问**：为拆而拆；说不清分布式事务代价。

#### [MS-02] 服务通信 / 进程端口

- **是什么**：服务=独立进程，监听端口；HTTP/RPC/MQ 通信。
- **为什么/原理**：进程隔离资源与故障域。
- **面试怎么答**：
  1. 同步：REST/gRPC；异步：MQ。
  2. 注册发现、配置中心、网关（了解名词即可）。
- **易错点 / 追问**：把「多个 Controller」说成微服务。

### 4.2 三个难点（已填，对照代码）

#### 难点 1：Excel 历史导入（样式语义 + 解析容错）

| 项 | 内容 |
|----|------|
| 现象 | 历史数据在 xlsx：A 列日期，B~G 题号+心得；**绿底=初刷、蓝底=复习、红字=卡住**；纯文本导入会丢失「复习」语义 |
| 原因 | 业务语义写在 Excel **单元格样式**里，不是单独字段；单元格文本格式也不统一 |
| 方案 | Apache POI 读样式判定 FIRST/REVIEW；正则解析 `题号. 标题` + 备注；按题关联 `attemptNo` 递增写入；单格失败跳过并汇总 errors，整文件 `@Transactional` |
| 取舍 | 不选「手填 CSV」：迁移成本高；不选「只导文本」：丢失复习类型。选 POI 是为兼容已有习惯 |
| 结果 | 一次性导入约 **30+** 条历史；导入结果返回 imported/skipped/errors，可重跑补漏 |
| 挂接八股 | `[SPR-04]` 事务边界 · `[JB-10]` 部分失败如何处理 · 解析/校验（可追问正则与异常） |
| 代码锚点 | `ExcelImportService#importExcel` |

#### 难点 2：每日复习推荐（业务规则落地）

| 项 | 内容 |
|----|------|
| 现象 | 题多了不知道今天复习哪几道；需要「滚动补位」而不是固定清单 |
| 原因 | 简单按日期排序不够：要兼顾**次数少优先**、**最久未刷**，且**今天已刷过的排除** |
| 方案 | `ReviewDashboardService#getPendingReview`：有记录的题 → 排除今日已刷 → 按 attemptCount 升序、再按 lastDate 升序 → **limit 3** |
| 取舍 | 未上完整 SM-2/Anki 算法（侵入大、对百题级收益有限）；先用可解释的双关键字排序，后续可加间隔复习字段 |
| 结果 | 仪表盘固定给出当日 3 道待复习 + 今日复习日志，形成「刷→记→再推荐」闭环 |
| 挂接八股 | `[COL-02]` Stream/排序 · `[SQL-01]` 若数据变大可改为 SQL `ORDER BY`+索引（现状内存过滤可接受） · `[JVM-01]` 时区与 `LocalDate` |
| 代码锚点 | `ReviewDashboardService`；时区：`TimeZoneConfig` + `Asia/Shanghai` |

#### 难点 3：领域模型（题 / 多解法 / 多次尝试）

| 项 | 内容 |
|----|------|
| 现象 | 一题有多种解法；同一题会刷多次；要统计进度、热力图、关联「这次用了哪个解法」 |
| 原因 | 单表「题目+最后一次结果」无法表达历史与多解；Excel 行列模型也不适合查询 |

4. **若只有这一个项目**：主动说「正式业务经验少，用该项目证明能独立交付 Spring + MySQL」，并补算法/八股。
